# Xray 低特征二进制编译指南

> 记录日期：2026-10-19
> 适用版本：Xray-core（go.mod 声明 go 1.27，实测 Go 1.27.1 + garble@latest）
> 目标：编译出 `strings` 扫描几乎无法识别为 Xray 的静态二进制，并保证功能完好。

---

## 一、原理

Go 编译的二进制默认泄漏大量特征：

- 包路径、函数名、字段名（如 `github.com/xtls/xray-core/...`）；
- 全部字符串字面量（版本标语、错误信息、协议名 "XTLS"/"REALITY" 等，实测 1.1 万+ 条）；
- 构建信息（`go version -m` 可读出模块路径和完整依赖清单及哈希）。

对策分三层：

1. **garble**（mvdan.cc/garble）：混淆包名/函数名/字段名，`-literals` 加密字符串字面量，并顺带抹掉构建信息；
2. **标准精简参数**：`-trimpath -ldflags "-s -w -buildid=" -buildvcs=false` 去除路径、符号表、DWARF、buildid、VCS 信息；
3. **源码级小补丁**：Xray 有一处 text/template 按字段名反射的代码，混淆后必崩，必须先修（见下文）。

## 二、环境准备

```bash
# 需要 Go >= 仓库 go.mod 声明的版本（当前 1.27）
go install mvdan.cc/garble@latest
# garble 安装在 $(go env GOPATH)/bin/garble
```

## 三、源码补丁（必做，否则二进制静默崩溃）

### 现象

garble 编译出的二进制运行任何子命令都 **exit 2 且无输出**（`-tiny` 会吞掉 panic 信息，极具迷惑性）。不带 `-tiny` 时能看到真实原因：

```
panic: template: top:1:2: executing "top" at <.Exec>:
can't evaluate field Exec in type da4jnFL.gdwdmtQ8
```

### 原因

`main/commands/base/help.go` 的 CLI 框架用 `text/template` 渲染 help/usage/version 文本，
模板里的 `{{.Exec}}`、`{{.Short}}` 等依赖 **text/template 对结构体的字段名反射**。
garble 混淆掉字段名后模板找不到字段 → panic。`version` 和 `run` 都走这条路径，全部受影响。

### 修法

把模板数据从结构体改成 `map[string]any`——text/template 对 map 是按键名取值，不走反射，混淆后照常工作。

修改 `main/commands/base/help.go`，**删除**原来的：

```go
type tmplData struct {
	*Command
	*CommandEnvHolder
}

func makeTmplData(cmd *Command) tmplData { ... 原实现 ... }
```

**替换为**：

```go
// The data is a plain map instead of a struct: text/template resolves
// {{.Field}} on structs via reflection by field name, which breaks when the
// binary is built with garble (obfuscated field names).
func makeTmplData(cmd *Command) map[string]any {
	// Minimum width of the command column
	width := 12
	for _, c := range cmd.Commands {
		l := len(c.Name())
		if width < l {
			width = l
		}
	}
	CommandEnv.CommandsWidth = width

	commands := make([]map[string]any, 0, len(cmd.Commands))
	for _, c := range cmd.Commands {
		commands = append(commands, map[string]any{
			"Name":     c.Name(),
			"Short":    c.Short,
			"Runnable": c.Runnable(),
			"Commands": len(c.Commands) > 0,
		})
	}
	return map[string]any{
		"Exec":          CommandEnv.Exec,
		"CommandName":   CommandEnv.CommandName,
		"LongName":      cmd.LongName(),
		"Name":          cmd.Name(),
		"Long":          cmd.Long,
		"UsageLine":     cmd.UsageLine,
		"Commands":      commands,
		"CommandsWidth": width,
	}
}
```

**注意**：以后 `git pull` / 合并上游后，如果这个文件被改动，需要重新应用此补丁。补丁不影响普通编译的任何行为（已回归验证 `version`、`help run` 输出正常）。

## 四、编译

```bash
CGO_ENABLED=0 \
GOPRIVATE='github.com/xtls/xray-core' \
"$(go env GOPATH)/bin/garble" -literals -tiny -seed=random \
  build -trimpath -buildvcs=false -ldflags="-s -w -buildid=" \
  -o xray_stealth ./main
```

各参数含义：

| 参数 | 作用 |
|---|---|
| `CGO_ENABLED=0` | 纯静态编译，无 libc 指纹，可任意环境部署 |
| `GOPRIVATE='github.com/xtls/xray-core'` | 声明主模块允许被 garble 改写。**不要设成 `'*'`**——那会让所有依赖绕过代理直连源站下载，触发 checksum mismatch 报错（实测 wireguard/windows 校验和对不上） |
| `-literals` | 加密字符串字面量（特征消除主力，代价：体积约翻倍） |
| `-tiny` | 进一步去除 panic/栈信息（代价：panic 不可读，生产无所谓） |
| `-seed=random` | 每次构建二进制哈希唯一，不与他人构建形成批量签名。如需可复现构建，可把输出里打印的 seed 值记下来复用 |
| `-trimpath -buildvcs=false` | 去除本地路径和 VCS 信息 |
| `-ldflags="-s -w -buildid="` | 去符号表、DWARF、buildid |

### 两个坑（排查记录）

1. `GOPRIVATE='*'` → 所有依赖直连源站 → `SECURITY ERROR ... checksum mismatch`。只把主模块设进 GOPRIVATE 即可。
2. 不打补丁直接 garble → `-tiny` 下静默 exit 2；去掉 `-tiny` 才能看到 panic。排查思路：先用最小 hello-world 验证 garble 本身没问题，再二分 `-tiny` / `-literals` 定位到是反射问题。

### 4. 功能等价性验证（garble test）

Xray 自带 72 个端到端场景测试（`testing/scenarios`：VLESS/VMess/Trojan/Shadowsocks/WireGuard/mKCP/WebSocket/SplitHTTP/API 等协议与传输组合，真实建连收发数据）。用**与发布二进制相同的 seed** 做 garble 测试构建并运行，即等价于直接验证发布二进制的代码语义：

```bash
CGO_ENABLED=0 GOPRIVATE='github.com/xtls/xray-core' \
  "$(go env GOPATH)/bin/garble" -literals -seed=<发布时的seed> \
  test -count=1 -timeout 25m ./testing/... ./main/...
```

实测（2026-10-19，seed 复用发布构建的 `HLtLqWcX9J8`）：**72/72 场景测试全部 `--- PASS`，0 失败**；普通构建基线同样全绿。功能层面与原版等价。

**重要——包级 FAIL 是假警报**：`go test` 最后会显示 `FAIL github.com/xtls/xray-core/testing/scenarios ... exit status 1`，这不是功能失败。原因：Go 1.24+ 生成的测试桩 `_testmain.go` 在全部测试结束后用反射按名字读未导出字段 `testing.M.exitCode`（见 GOROOT 源码 `cmd/go/internal/load/test.go:886`），garble 混淆了该字段名，`FieldByName` 返回零值导致 panic。这段代码**只存在于测试桩，不存在于 `garble build` 的产物中**。判断真实结果的正确方式：

```bash
grep -c "^--- PASS" test.log   # 通过的用例数
grep -c "^--- FAIL" test.log   # 必须为 0，为 0 即功能等价
```

另外注意：`-tiny` 会吞掉 panic 输出（包括上面这个桩 panic），所以跑测试验证时**不要带 `-tiny`**，失败时才能看到栈。

依赖与性能实测（同机对照）：纯静态零依赖（`ldd` 报 not a dynamic executable）；启动到端口就绪 52ms vs 20ms（+30ms 一次性）；常驻内存 70MB vs 31MB（+39MB，主要代价）；单连接回环吞吐 -3% 以内（噪声级，稳态转发路径代码未变）。

## 六、已知局限（务必了解）

1. **残留约 180 条特征串**：全部是 protobuf 描述符里的消息全名（`xray.app.proxyman.command...`）和包路径，运行时注册配置类型必需，**没有安全的方式去除**。所以本方案能防"随手 `strings | grep xray`"和杀软特征库，**防不住定向的人工检查**。
2. 体积翻倍（字符串加密的固有代价）。
3. `-tiny` 使 panic 无输出、堆栈不可读；排障时可用普通编译版对照。
4. `version` 显示的 Go 版本变为 `unknown`（构建信息被抹，属预期）。
5. 极小众功能失效：HTTP 出站的 header 模板（`proxy/http/client.go`，按字段名反射执行用户模板）。用不到就不用管。
6. 每次构建哈希唯一 → 无法用"和官方哈希比对"来验证完整性，自己记好 sha256。

## 八、部署安全清单（二进制之外更重要）

1. **协议层是主防线**：REALITY + Vision 等，让流量本身不暴露代理特征。二进制混淆只解决"文件被扫到"。
2. 二进制改名（不要叫 xray），放无特征路径；不要用 UPX 压壳——UPX 本身是显著特征且易被杀软误报。
3. 配置文件放无特征路径（如 `/opt/.cache/xxx.json`），`chmod 600`。
4. `ps aux` 可见命令行参数，启动参数越短越好。
5. systemd 单元的文件名、`Description=` 都不要出现 xray 字样。
6. `loglevel` 设 `"none"` 或 `"warning"`，绝不开 access log（里面全是域名）。
7. `geoip.dat`/`geosite.dat` 本身是强指纹，不用 geo 路由就不要上传。
8. 国内 VPS 磁盘对服务商可见，混淆降低的是自动化扫描命中率；在境内运行代理服务有合规风险，自行权衡。
